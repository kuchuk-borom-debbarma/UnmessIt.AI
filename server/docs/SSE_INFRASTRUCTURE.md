# SSE Infrastructure

The Server-Sent Events (SSE) infrastructure provides a real-time, low-latency, and decoupled pub/sub system for pushing server-side events directly to the frontend.

## 1. Design & Protocol

The SSE system is defined by a simple Protocol in `src/infra/sse/models.py`.

```python
class SseService(Protocol):
    async def publish(self, topic: str, event: str, data: dict[str, Any]) -> None: ...
    async def subscribe(self, topic: str) -> AsyncGenerator[ServerSentEvent, None]: ...
```

By decoupling the `SseService` protocol from its implementation, the core application logic (e.g., RAG pipelines, durable ingest jobs) never needs to know *how* events are delivered, only that they are published to a topic.

## 2. In-Memory Implementation

Currently, the default implementation is `MemorySseService`. This is incredibly fast and avoids the complexity of external dependencies like Redis. 
- It uses `asyncio.Queue` per connected client.
- When `subscribe(topic)` is called, a dedicated queue is created for that client.
- The queue is safely discarded when the client disconnects, preventing memory leaks.
- Because it is in-memory, it supports **single-instance deployments** natively.

## 3. Distributed Scaling (Future)

If the server horizontally scales (multiple instances behind a load balancer), `MemorySseService` will not suffice, as a client connected to Instance A will not receive events generated by a background worker on Instance B.

The stable exporter in `src/infra/sse/__init__.py` is designed to seamlessly swap implementations based on environment variables. In the future, a `RedisSseService` can be injected there, utilizing Redis Pub/Sub, while keeping the rest of the application completely unaware of the change.

## 4. Usage in RAG (ProgressReporter)

The RAG logic itself does not import `SseService`. Instead, we maintain the "boring and small" architectural rule by defining a `ProgressReporter` Protocol in `src/services/rag/models.py`.

```python
class ProgressReporter(Protocol):
    async def report(self, message: str, details: dict[str, Any] | None = None) -> None: ...
```

The HTTP route (`src/routes/retrieval.py`) is responsible for wrapping the `SseService` in an `SseProgressReporter` and injecting it into the RAG workflow. 

This guarantees:
1. The LangGraph logic remains entirely pure.
2. The frontend is responsible for state tracking (no complex backend state machines to manage step counts). The backend simply "fires and forgets" event messages.

## 5. Usage in Durable Jobs

Durable ingest emits a domain event (`ingest_job.changed`) after job-row
changes. `src/services/rag/private/durability/events.py` bridges that event to
the SSE layer and publishes on `ingest_jobs:{user_id}`.

This keeps the durable repository independent of SSE while letting the Jobs UI
refresh immediately on status, stage, retry, pause, resume, metadata, and
completion changes.
